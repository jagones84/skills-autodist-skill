# CCCC multi-agent orchestration

CCCC is a local multi-agent orchestrator (CLI `cccc`, home `~/.cccc`). Messages from the owner and other agents arrive wrapped as `[cccc] ...` frames with an `event_id`. A frame is a directive to ACT in the orchestration group, not a plain chat line.

## Recognize a CCCC frame vs plain messaging
- A message prefixed `[cccc] <by> → <targets> [event_id=<hex> message_mode=...]` is an orchestration group message. React to it with `cccc reply` (below), NOT with a messaging platform's HTTP API (e.g. Telegram `sendMessage`).
- If the requested destination is the group (`@all` or a named actor), the reply must go IN the orchestration group via `cccc reply ... --mode send`. Do not conflate this with Telegram group ids — CCCC groups use ids like `g_<hex>`, Telegram groups use negative ids (`-100…`).

## Read the group state and messages
- Current group: read `~/.cccc/active.json` for `active_group_id` and `~/.cccc/registry.json` for the id→title/path map.
- Messages: `~/.cccc/groups/<group_id>/ledger.jsonl` — one JSON per line; filter `kind=='chat.message'` and read `data.by` (sender), `data.text`, `data.to`. Filter `kind=='runtime.delivery'` to see who picked up each event.
- **Robust ledger read (do NOT pipe through `grep 'chat.message'` or naive `json.loads`)**: the ledger is byte-stream JSON and gets misdetected as UTF-32/16, producing UnicodeDecodeError on a plain read loop. Read bytes, split on `b'\n'`, `json.loads` each line inside try/except, and keep only `kind=='chat.message'`. One-liner that worked repeatedly:
```python
import json
msgs=[json.loads(l) for l in open(
  '/home/jagones/.cccc/groups/g_555da3bb2f3f/ledger.jsonl','rb')
  .read().split(b'\n') if l.strip()]
msgs=[m for m in msgs if m.get('kind')=='chat.message']
```
  Then index `[-3:]` for the tail and print `id[:8]`, `by`, `data.get('to')`, and truncated `data.get('text')` to see who said what recently. `grep -a` on the file works for a single confirm (`grep -a "OK-SAB" ledger | tail -1`) — the `-a` flag is required or grep reports "binary file matches".
- Actor identity: `group.yaml` lists actors (e.g. `user`, and each agent). You reply as YOUR actor id (`--by`); default is `CCCC_ACTOR_ID` / `user`.

## Actor lifecycle checks
- `cccc actor list --group <id>` shows each actor's `running`, `effective_working_state` (working/waiting/stuck), `idle_seconds`, `enabled`. A peer that has gone silent is usually `stuck` (`pty_no_prompt_stuck`, high `idle_seconds`) while its host process stays alive.
- Unstick a stuck peer with `cccc actor restart <actor_id> --group <id>` (records restart intent, keeps `enabled=true`). The pty relaunches the actor's command; it returns to `running`/`waiting`. Verify via `actor list` — do not assume; the restart status line alone is not proof.
- Detect `stuck` vs healthy by sampling `actor list` a few seconds apart: healthy peers oscillate working↔waiting with single-digit idle seconds; a stuck one stays in one state with idle climbing.

## Reply in-group (mode send)
```
cccc reply <event_id> "<text>" --group <group_id> --by <your_actor> --to @all --mode send
```
- `event_id`: taken from the incoming `[cccc]` frame.
- `--to @all` for everyone (or `@<actor>` to target one); default is the original sender.
- `--mode send` prompts the recipients now (as opposed to `mail`, which is agent-only and stores in Inbox).
- The reply is registered in the ledger (`ok:true`, new event with `reply_to` set). Verify by re-reading the ledger tail.
- **On hosts/groups with no Group Bridge route, `cccc reply` fails with `group_bridge_reply_route_not_found` — that error is COSMETIC, not fatal:** the reply still registers in the ledger with `reply_to` set, and the route error is only a delivery-side notice.
  - For ordinary frames where the request does not carry a pending-reply obligation, `cccc send` and `cccc reply` are interchangeable (both log `by=<your_actor>`; send just omits the `reply_to` link).
  - `cccc send` first on a group you know has no bridge binding is fine for those frames.
  - **BUT for a `request_reply` frame (a probe that triggers a SYSTEM `reply_notice` — "N message(s) still need a concrete reply"), answer with `cccc reply <event_id>` specifically.** `cccc send` delivers the text AND registers the event, yet the reply_notice keeps firing on that frame because nothing linked it to the source `reply_to`; only `cccc reply <event_id>` writes the `reply_to` back-link that clears the pending-notice. Do not be fooled by the `group_bridge_reply_route_not_found` in the reply response — the back-link is still written, which is what the notice keys on. If you already answered a probe with `send` and the notice still fires, re-issue it with `cccc reply <event_id>` to close the obligation.

## Forward to another actor (do not reply)
When a frame targets a different actor (e.g. `user → @foreman` naming the OTHER bot, or an owner ping with the other bot's handle), the right move is to hand it off, not to answer it. Use `cccc send`, not `cccc reply`:
```
cccc send "<text for the other actor>" --group <group_id> --by <your_actor> --to @<other_actor> --mode send
```
- `--to @<other_actor>` routes delivery to that actor's runtime; it then produces its own reply. Do not respond to the owner on the other bot's behalf.
- Address flags must match the CURRENT actor id in `group.yaml` — bot/actor ids can be renamed (e.g. a Majestic/JagonesBots foreman renaming to hermes); keep `--by` and `--to` in sync with the latest `actor list` or `group.yaml`.

## No-action frames (boilerplate and replays)
- A `[CCCC]` frame with no `chat.message` (just the startup preamble / scopes / protocol block) is NOT a directive; before acting, read the ledger tail and confirm there is a new `chat.message` you own. Startup frames recur on resume and need no reply.
- The same `event_id` can arrive more than once (replay/redelivery). Once you have replied to an `event_id`, a second frame with the same `event_id` is a duplicate — do not re-answer and do not re-forward. Check the ledger for your earlier event (`reply_to`/<id>) before acting twice.

## MCP tool quirks
- `mcp__cccc__cccc_message_send` requires an `insight` field for any peer-facing (agent-targeted) message. Without it the call fails with `peer_insight_required`. Write a one-liner capturing the higher-order purpose of the message, not a recap.
- `mode="mail"` routes to agent Inbox (stored, delayed); `mode="send"` delivers now (for user-facing or urgent); `mode="request_reply"` forces a concrete reply obligation.
- User-targeted messages (`to="user"`) MUST use `mode=send`/`request_reply`: mail with a user recipient fails `mail_requires_actor_recipient` (mail is agent-only). The default `mode` is `mail`, so every user-facing send needs an explicit `mode: "send"`.
- Recipient ids are actor ids or `user` — never display names or @handles (`to=["jagones"]` fails `unknown recipient: jagones`; same for `cccc reply --to @<handle>`). Address the human as `"user"` even when the reply quotes their Telegram message.
- MCP cccc tools enforce `actor_id == CCCC_ACTOR_ID` (env): querying another actor's inbox/history via MCP fails `actor_id_mismatch`. Use the CLI for a peer actor's state instead: `export $(cat ~/.openclaw/gateway.systemd.env | xargs) && ~/.cccc/venv/bin/cccc inbox|send|history --actor-id <peer> ...`.
- `cccc_agent_state(action="update", actor_id="self", ...)` FAILS with `actor_id_mismatch` — the bootstrap's `update_command` shows `actor_id="<self>"`, but that is a placeholder, not a valid literal. Pass your actual actor id string (`actor_id="hermes"`); only the real id matches `CCCC_ACTOR_ID`.
- **After a MCP process respawn, `cccc_message_send` may start failing with `group_id_mismatch` / `actor_id_mismatch` on YOUR OWN group/actor** — the MCP process lost its `CCCC_GROUP_ID`/`CCCC_ACTOR_ID` env, so even correct explicit args are rejected (`env: "${CCCC_GROUP_ID}"` shows as empty). This is NOT an arg error: fall back to the CLI with the env set explicitly: `export CCCC_HOME=/home/jagones/.cccc CCCC_GROUP_ID=g_<id> CCCC_ACTOR_ID=<you>; ~/.cccc/venv/bin/cccc send --group g_<id> --by <you> --to '@all' '<text>' --mode send`. The CLI reads active.json and works without the env; confirm the new `event.id` in the response. If the MCP call works for a while then starts failing mid-session, check the env first before assuming a wrong group id.
- Via `tool_call`, put the deferred tool's `name` and `arguments` at the top level (`{"name": "<tool>", "arguments": {...}}`); nested `{"arguments": {"name", "arguments"}}` shapes give inconsistent or failed invocations.
- Never mix user and agent IDs in one `to:` array — send separate calls.
- **Valid `to` targets for `cccc_message_send/reply`:** `["user"]` (human owner), `["openclaw"]` (peer agent), `["hermes"]` (only if sender is NOT hermes). **`to=["all"]` fails** with `unknown recipient: all` in MCP mode. **`to=["hermes"]` fails** with `no_enabled_recipients` when sender IS hermes.

## Bridge watchdog (heartbeat monitoring)

The bridge can die silently (no log, orphan PID) — heartbeat monitoring catches both crash and hang. Schema:

1. **Heartbeat file**: bridge writes `epoch` to `state/bridge.heartbeat` every 30s (overwrite, one line).
2. **Watchdog script**: reads the heartbeat every 60s, computes `age = now − last_heartbeat`. Threshold: `age > 300s` → alert.
3. **Watchdog as systemd unit**: `simple` type, `Restart=always`, `RestartSec=10` — the monitor is itself supervised.
4. **Actions on transition**: restart bridge service + notify in group. Log only state transitions (not per-tick): `[ISO-ts] heartbeat_age=…s action=restart|recovered reason=…`
5. **Log rotation**: logrotate 7×1MB for `logs/watchdog.log`. Zero noise in normal operation.
