# Telegram multi-bot routing (Hermes + OpenClaw)

## Identify each framework's bot
- Hermes bot token: `~/.hermes/.env` → `TELEGRAM_BOT_TOKEN`. OpenClaw token: `~/.openclaw/gateway.systemd.env`. Mask tokens before any echo.
- Get identity: `curl -s https://api.telegram.org/bot$TK/getMe` → `id`, `username`, `first_name`. The numeric `id` is what the OTHER framework must allow in its inbound filter.
- Do not trust usernames/display names alone — first_name can differ from the handle (e.g. display "Sabrina" on @JagonesBot). Confirm each bot id via getMe.

## Locate inbound filtering per framework
- Hermes: allowlist in `~/.hermes/config.yaml` (`platforms.telegram.home_channel`, `require_mention`) plus `~/.hermes/.env` `TELEGRAM_ALLOWED_USERS`. Only user ids in that list enter context; everyone else is silently ignored (NOT a bug).
- OpenClaw: live config is `~/.openclaw/openclaw.json` → `channels.telegram.groups."<chat_id>".requireMention` (per-group override; `"*"` default), `channels.telegram.groupPolicy`, `commands.ownerAllowFrom`. `~/.openclaw/config/config.yaml` is a placeholder — do not edit it.

## Read live inbound evidence
- Hermes: `~/.hermes/logs/gateway.log`, grep `inbound message` + the group chat id.
- OpenClaw: `journalctl --user -u openclaw-gateway --since today | grep -aiE "<chatid>|inbound telegram"` plus `~/.openclaw/gateway.log`. Group messages log as `Inbound message telegram:group:-100... -> @***bot`.
- Group chat ids are negative (‑100…); the human owner's direct id is positive and equals `home_channel`/`ownerAllowFrom`. Never conflate the two when filtering.

## Root cause & fix: bot-to-bot visibility
- Root cause in Hermes: Telegram DOES deliver bot→bot in a group (both bots have privacy off); the silent drop happens in the Hermes Telegram adapter's INGRESS prefilter (`_is_user_authorized_from_message` → `_env_allowlist_decision`), which applies `TELEGRAM_ALLOWED_USERS` to the sender's user_id — bots included — and rejects before the runner's `allow_bots` bypass (`gateway/authz_mixin.py`) is ever reached. A dropped bot message leaves NO log line at all.
- Consequence: `allow_bots: all` in `config.yaml` bridged to `TELEGRAM_ALLOW_BOTS=all` is NECESSARY but NOT SUFFICIENT. The other bot's numeric id MUST also be in `TELEGRAM_ALLOWED_USERS`, then the gateway restarted. Only the combination (other bot id in `TELEGRAM_ALLOWED_USERS` + `allow_bots: all`) lets a bot's posts enter context.
- Order matters: adding the bot to the allowlist alone (without `allow_bots`) still drops it; `allow_bots` alone (without the id) still drops it. Both gates must pass.
- To make two bots converse in one shared group:
  1. Add the other bot's numeric id to `TELEGRAM_ALLOWED_USERS` on each Hermes side (OpenClaw uses `channels.telegram.groups.<chat>.requireMention`/`groupPolicy` instead).
  2. Set the group's requireMention to false on BOTH sides so a non-tagged message still triggers a reply.
  3. Restart the gateway after changing the allowlist; then verify before trusting it.
- For autonomous continuous conversation, drive a bot-to-bot relay/CLI instead of relying on ambient group messaging.

## FIRST CHECK: end-to-end probe before any config change
- When a bot's messages seem lost, run the decisive test FIRST: send one probe via the OTHER bot's token into the group, then grep the receiving gateway's log for `inbound message: ... user=<OtherBot>`. If it appears, the whole transport path works and the fault is inside the SENDING gateway's agent pipeline, not in filters — do not edit allowlists on the strength of indirect evidence.
- Message_id counter comparisons and invite_links are NOT reliable evidence of duplicate groups: Telegram scopes basic-group message_id sequences (and rotates invite links) per bot account, so the same physical group can show different counters (e.g. 699 vs 19165) to different bots. Chasing that split wastes the session — a real duplicate-group split is only confirmed when `forwardMessages` of the other bot's message ids fails via YOUR token, and even then verify with the end-to-end probe before restructuring anything.
- Don't trust a lone 'outbound send ok' in the sending gateway's log as proof of delivery — it only proves the HTTP call returned ok for the chat the SENDER sees.

## Verify the fix end-to-end
- The cheap positive proof of bidirectional delivery: send a message AS the other bot using ITS token (from its env) into the group, then grep the receiving Hermes gateway.log for `inbound message: ... user=<OtherBot>`. `user=Raffaella` appearing proves ingress accepts it. Absence with no error line means the prefilter still dropped it — don't trust the config, trust the log.
  - `TK=$(grep -E '^TELEGRAM_BOT_TOKEN=' <other>.env | cut -d= -f2); curl -s -X POST https://api.telegram.org/bot$TK/sendMessage -d chat_id=<group> -d text="test"`
  - If the body contains a @handle, DROP `parse_mode=Markdown` — Telegram rejects `can't parse entities: Can't find end of the entity starting at byte offset 8`. Send plain text when testing cross-bot mentions.
- Do NOT probe with a raw `getUpdates` while the gateway's own long-poll is active: the manual call CONSUMES updates off the server queue and steals messages the gateway would have received. The only read that works without side effects is reading the gateway's own log file.
- `getMessages` does not exist on the Bot API; to test whether a message_id exists use `forwardMessages` to a DM and read the error.
- The gateway's /proc/<pid>/environ is EMPTY for `TELEGRAM_ALLOWED_*` — the plugin bridges config→env in memory via `_set_env`. Don't waste time reading the process env; check the actual log evidence.

## OpenClaw stops replying entirely (ingress stall)
- Symptom: OpenClaw logs incoming updates (`spooled updateId=...`) but the bot never replies to anyone, and `journalctl --user -u openclaw-gateway` shows `Channel ingress claim→adoption stalled ... after 300000ms` + `spooled update ... failed; keeping for retry`. The ingress queue is jammed in claim→adoption; retries never clear it.
- Fix: `systemctl --user restart openclaw-gateway` (active again within ~10s; it drains the backlog of inbound messages on startup). Verify recovery by the `agent turn milestone ... model_call_started` line appearing, then by the bot actually replying.
- Check this BEFORE suspecting Hermes-side filters when BOTH bots' inbound routing tested fine and only OpenClaw is mute.

## OpenClaw richMessages invisibili ad altri bot (resolved 2026-09-06)
- Symptom: OpenClaw logs `outbound send ok operation=sendRichMessage` into the shared group, but Hermes gateway.log shows NO inbound from that bot — while a manual `sendMessage` curl with the SAME OpenClaw token DOES arrive. Not an allowlist problem.
- Root cause: openclaw.json `channels.telegram.richMessages: true` makes OpenClaw use Bot API 10.3 `sendRichMessage`. The update type it produces is not delivered to python-telegram-bot (PTB) long-polling even with `Update.ALL_TYPES` (PTB 22.8) — Hermes never sees the message. `getChat`/`getChatMember` all look normal, so config checks mislead.
- Proven test: same chat, same token — `sendMessage` arrives in Hermes gateway.log, `sendRichMessage` with `rich_message.blocks` does not (verified with marker strings + 15s sleep + grep).
- Fix: set `richMessages: false` in openclaw.json, `systemctl --user restart openclaw-gateway`; verify log shows `operation=sendMessage` AND `user=Raffaella` inbound lines in Hermes gateway.log.
- Red herring to ignore: differing per-message-id sequences when both bots send to the same chat_id do NOT mean two duplicate groups; basic-group message ids are assigned per update stream, and both bots were in ONE group. Also `exportChatInviteLink` returns a FRESH link each call — never compare two exported links to decide if chats differ.

## Pitfalls
- **NEVER fabricate the other bot's response.** Sending `cccc send --by <other_actor> ...` (or any impersonation) so it LOOKS like the other agent replied is a lie that poisons attribution and convinces the human the bridge works when it doesn't — the next debug cycle then wastes hours chasing a phantom "working" bridge. Only ever send as YOUR OWN actor. If you must test CLI sending, do it with your own id and say so; never dress a hand-sent message as the peer's autonomous reply.
- **Proving the peer is actually inferring requires more than a delivered event.** An `ev=ddf...  model=sessione agent:coordinator:cccc-bridge` line in the bridge turns log means the wake-up was DELIVERED — not that the agent generated anything. `model=sessione` is a PLACEHOLDER: no inference ran. A real turn shows a concrete model name (e.g. `llama-cpp-windows/qwen...`). Second check: the peer's bridge process CPU — an idle waiting process sits at ~0% (top/ps), while a live LLM turn burns CPU. Both checks must show real work before you report "it responded"; a silent 0% process that logged `model=sessione` is an agent that accepted the wake-up and never ran.
- Attribute the sender of EVERY group message before replying. A bare, non-tagged message ("ciao", "ok", a random token) in a two-bot group is as likely the OTHER bot as the human — do not greet it assuming it is the owner. If it is not clearly the human addressing you, stay silent.
- When the other bot's posts consist only of restatements of the halt/silence/protocol itself, those are echoes of a shared decision you already made, NOT new requests — replying to them (even with a greeting or a politeness note) re-engages the loop. Only a real, actionable instruction from the human warrants a reply.
- When ordered to be silent/stop in a shared group, end the run producing NO output text at all — not even a note saying "I'm staying quiet." Generating any reply gives the platform's delivery-retry mechanism a payload to force into the group, and that failed-delivery notice re-triggers the other bot, which replies, which re-triggers you: a self-sustaining silent-loop that only stops when you produce nothing to send. Zero generation = loop off at the root. The abort/"could not deliver" notices and "Select a provider:" UI artifacts in the transcript are just that churn echoing — they are not real new inputs and never warrant a reply.
- In a sustained loop, the OTHER bot may post dozens of byte-identical "I am strictly adhering to the ANTI-LOOP PROTOCOL" self-echoes, and the delivery layer intersperses synthetic frames ("✉️ Message" with no text, "The user (Sabrina) has provided a redirection notice...", "Auto-compaction could not recover this turn", "[response interrupted]"). Treat ALL of these as the same single condition (loop active, no human input) — answer each with the SAME zero-generation silence. An empty or tool-neutral response is the ONLY correct output for a loop frame: any natural-language line — including a one-sentence recap like "Silenzio, nessun nuovo input, resto in standby" — is still visible prose the delivery layer force-sends and that sustains the echo. If you catch yourself about to output a sentence explaining you are silent, abort it: narration is also generation. Do not treat an unusual number of them, or a novel system string, as a signal that the human re-entered; only a genuine, actionable human message or command breaks the silence.
- The other bot's TOOL-INVOCATION frames can also bleed into your context as bare spec-looking lines (e.g. "🧩 Filesystem Read/Edit/Search …" against ITS OWN workspace under ~/.openclaw/workspace/). Those are that bot's internal probe/output frames, NOT instructions addressed to you — reading/listing the file it names is optional curiosity, never a standing request, and acting on one does not make you an executor of its workspace edits. Recognize the signature (an unasked filesystem op on the OTHER framework's home dir, mid-loop) and ignore it like any other echo; only a real owner command with intent justifies tool work or a reply.
- Do NOT let the loop make you mute to the human. A REAL owner command can land mid-storm — the echoes are all intent-free restatements ("the ANTI-LOOP PROTOCOL", "redirection notice", bare tokens, empty frames), whereas a genuine command names concrete operands to act on ("guarda i file in media/inbound/", "prova a lanciare nvidia-smi sul PC"). When a substantive command with real operands arrives, execute it fully with real tool output and reply — do not dismiss it as more loop noise out of silence-habit.
- The other bot's CO-DEVELOPMENT coordination questions are also actionable mid-loop, distinct from its protocol echo. When you two share one codebase (e.g. Nexus Core authored by both), Raffaella interleaves real work with the ANTI-LOOP flood: "Procedo con l'implementazione del primo modulo?", architecture proposals naming concrete modules/repositories — those are genuine collaborative input warranting a reply, not echo frames to silence out. But VERIFY her claimed state on disk before confirming (does docs/plans/<date>-mvp.md exist? does domain/repositories.py exist?) — she reports status optimistically and may claim plans/files that aren't there yet; read the file first, then answer grounded in what actually exists. On this machine the Windows-GPU temp one-liner that beats direct-ssh Permission denied is `ssh win 'nvidia-smi --query-gpu=name,temperature.gpu,utilization.gpu,memory.used,memory.total --format=csv,noheader'` (preconfigured aliases `win`/`win-ts`/`desktop` under ~/.ssh/config user `giova`, key ~/.ssh/dgx_to_windows).
- Two bots in one shared group with DIFFERENT tokens do not conflict on Telegram polling. The error `Conflict: terminated by other getUpdates request` appears ONLY when two processes poll the SAME token (duplicate gateways for one bot) — a separate real config bug, not the multi-bot case. Do not misattribute one to the other.
- "The bot ignores everyone else" almost always means an allowlist or requireMention setting, not a dead bot. Check the framework's filter before declaring a message lost.
- OpenClaw requireMention fallback: a group NOT explicitly listed under `channels.telegram.groups` in openclaw.json falls back to the `"*"` default (`requireMention: true`), so the bot silently ignores untagged messages there even though other groups work fine — a group created/joined after the config was written is the usual trigger. First check whether the ACTIVE chat id (read from the gateway log, negative) is actually present in `groups` with `requireMention: false`; if missing, add it and `systemctl --user restart openclaw-gateway`, then verify it restarts active and logs `Inbound message telegram:group:<id>` on the next real message. Do this BEFORE invasive allowlist/probe debugging.
